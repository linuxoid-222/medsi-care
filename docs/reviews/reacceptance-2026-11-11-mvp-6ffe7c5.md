В дереве уже был неотслеживаемый [исходный отчёт о приёмке 0233065](acceptance-2026-11-11-mvp-0233065.md); он не изменён.

## N1 — сохранение после потери ответа

1. **Браузер, реальный commit и потеря ответа.** Chromium 155.0.8059.84 записал синтетический WAV с виртуального микрофона через MediaRecorder; транскрипт вернул локальный faster-whisper. При первом нажатии «Сохранить транскрипт» Playwright переслал POST реальному FastAPI, получил 201 и проверил сохранённые ID и ключ прямым SELECT из PostgreSQL. Затем ответ для вкладки прерван через `route.abort("connectionreset")`. Повторное нажатие послало тот же UUID, вернуло 201 и тот же ID; в БД осталась одна строка. Кнопка показала «Транскрипт сохранён» и стала недоступна.
2. **Повтор и конфликт на API.** В отдельной пробе остановил обработчик на чтении снимка после commit и до формирования успешного ответа. Повтор через другой SQL repository вернул ID, уже видимый из второго соединения. Краевые пробелы нормализовались. Восемь одновременных POST с новым общим ключом вернули один ID и создали одну строку. Уже использованный ключ с другим текстом дал 409. Новый ключ с исходным текстом дал отдельный ID. SQL-триггер, отклонивший INSERT до commit, дал 500 и не оставил строки; после снятия триггера тот же запрос с тем же ключом дал 201.
3. **Область ключа и доступ.** Индекс уникален по `(profile_id, creation_key)`. С тем же UUID и исходным текстом caregiver и тестовая подписанная identity другого профиля получили 403 на POST к профилю владельца, без ID или текста записи; запрос без токена получил 401. Чтение записи identity другого профиля также дало 403. На уровне SQL repository тот же UUID сохранился независимо во втором синтетическом профиле, а перекрёстный поиск по ID не вернул чужих строк. Публичный MVP API обслуживает один профиль, поэтому второй профиль проверялся через репозиторий и подписанную тестовую identity. Отдельная изоляция между двумя владельцами с правом записи в один профиль не заявлена: такой роли доступа в MVP нет.

**Перезагрузка и текст UI.** Во второй записи тем же WAV получился тот же текст и новый UUID. После её commit ответ снова был прерван; при reload распознанный текст и кнопка повтора исчезли. «Открыть последнюю запись» вернула именно уже сохранённый ID. Новая запись того же WAV после reload получила ещё один UUID и ID. Это соответствует документированному сроку жизни черновика; ключ, уже записанный на сервере, сохранился вместе с записью.

**Неблокирующее замечание к интерфейсу.** Воспроизведение: отбросить 201 после commit, как описано выше, и прочитать «Не удалось сохранить транскрипт. Проверьте связь и повторите попытку». Совет работает, пока открыт черновик, но текст звучит как подтверждённый отказ сохранения, хотя исход неизвестен вкладке. Он не предупреждает о потере черновика при reload и не подсказывает проверить последнюю запись. Влияние: если вместо проверки истории пользователь после reload повторно запишет ту же фразу, появится отдельная строка. Для MVP штатный повтор в открытой вкладке работает, а сохранённая запись доступна из истории. Точнее было бы сообщать, что сервер не подтвердил сохранение, предложить повторить в этой вкладке и после reload проверить последнюю запись.

## N2 — повторная загрузка demo

- **D → D+1, одинаковые параметры и seed.** Загрузил 21 день с `anchor_date=2026-11-10`, `seed=20261110`, затем 11 ноября с `reset=false`. Повтор одинаковых параметров до и после смены даты оставил те же ID и те же данные. После перехода осталось 63 измерения и 21 check-in генератора. На 20 пересекающихся локальных датах было по одной записи на метрику и время. ID предыдущего набора исчезли. Смена seed на `20261111` снова заменила ID при тех же количествах. Seed в этом генераторе меняет идентичность набора; при той же дате фиксированный числовой паттерн остаётся прежним.
- **Атомарная видимость и rollback.** SQL-триггер перед INSERT в `check_ins` задержал замену на PostgreSQL advisory lock, когда удаления уже были выполнены внутри транзакции. Во втором соединении снимок пяти таблиц полностью совпал с прежним. После освобождения блокировки был виден полный новый набор. Отдельный триггер отклонил INSERT при смене seed: loader вернул 500 как с `reset=false`, так и с `reset=true`; обе попытки сохранили прежнее состояние observations, check-ins, facts, events и notifications.
- **Пользовательские данные и история.** После смены даты и seed сохранились вручную созданные измерение давления, check-in и подтверждённый ручной факт. Подтверждённая слабость на сгенерированном check-in вошла в событие мониторинга. После смены seed этот исходный check-in стал недоступен (404), его факт и исходные измерения удалены. Через GET events прочитал прежний снимок целиком: исходные observation IDs, check-in и fact ID, цитату, время, ревизии и версию правил. Уведомление caregiver сохранилось вместе с `read_at`. Факты, привязанные к удаляемым строкам генератора, удаляются по контракту; сохранённое событие остаётся источником исторического снимка.
- **Числовой attention.** Анализ с cutoff в конце первого сценария (`2026-11-10T12:00:00+03:00`) и второго (`2026-11-11T01:00:00+03:00`), а также после смены seed дал `attention` по всем трём метрикам: 5 ч, 25 мин, 90 bpm при baseline 8 ч, 65 мин, 70 bpm и 14 исторических датах для каждой метрики. Cutoff нового дня был раньше последующего подтверждения слабости. В diff кандидата относительно 0233065 нет изменений числового ядра и порогов; результат объясняется чистой выборкой.

## N3 — конкурентные подтверждения

Два экземпляра `DatabaseStore` использовали разные пулы и PostgreSQL backend PID. В тестовом приложении запросы FastAPI направлялись к нужному экземпляру; ожидания управлялись барьерами в тестовой обвязке, а SQL-операции и транзакции были реальными.

| Воспроизведение | Наблюдение |
| --- | --- |
| Два одновременных POST одного набора для `text_revision=1` | Полностью одинаковые ответы: `facts_revision=1`, прежние ID и `confirmed_at`, одно safety-событие и по одному уведомлению владельцу и caregiver. GET из другого репозитория согласован с POST. |
| Одновременный старт двух разных валидных наборов; отдельно A задержан после commit, B завершён до доставки A | Два набора получили ревизии 1 и 2. В контроле A с `chest_pain/present` вернул ревизию 1 даже после ответа B с `shortness_of_breath/present` и ревизией 2. Верхние метаданные, факты, ID и времена совпали с соответствующими коммитами. GET записи и списка вернули факты и метаданные последней ревизии. |
| A подтверждает, B правит текст после commit A, но до ответа A | A сохранил метаданные и safety-provenance редакции 1. Последующий GET вернул редакцию 2 с новым текстом, пустыми текущими фактами и `confirmed_at=null`. Историческое событие A сохранилось. |
| POST прочитал старый текст и прошёл API-валидацию; PATCH коммитится перед SQL-подтверждением | POST старой редакции получил 409 на проверке репозитория. Новая редакция и таблицы не изменились от отклонённого POST; корректное подтверждение редакции 2 прошло. |
| SQL-триггер отклонил уведомление caregiver при попытке заменить уже подтверждённый набор | 500; прямой SQL и GET подтвердили сохранность прежних фактов, ID, ревизии и времени. Новых событий или уведомлений не осталось. Повтор без триггера сохранил следующий номер ревизии. |

У каждого успешного содержательного safety-подтверждения сверены сохранённое событие, версия `safety-v1`, check-in/fact ID, категория, polarity, цитата, время и обе ревизии; оба уведомления ссылались на ID события именно этого подтверждения. При равных наборах события не дублировались. Для разных наборов порядок коммитов может различаться, но смешивания снимков не наблюдалось.

## Связанные регрессии и границы проверки

- **F7, независимый контроль анализа:** восемь параллельных POST через два репозитория вернули один и тот же снимок; SQL показал одно событие и два уведомления. После чтения уведомления caregiver более поздний cutoff с теми же значимыми входами вернул первый снимок и не изменил `read_at`.
- **Backend:** 186 passed, 5 skipped. Пропущены только варианты memory для SQL-only кейсов; PostgreSQL-варианты выполнены. Пройдены связанные проверки RBAC, lifecycle фактов, ручного пути при отказе extraction, недостатка данных, analysis/trends, safety и уведомлений. Файлы исследовательских тестов намеренно исключены.
- **Frontend:** 15 passed, production build прошёл в отдельной копии `frontend` из HEAD. Сохранилось предупреждение Vite о чанке больше 500 kB. Браузерный путь проверялся на этой сборке и отдельном FastAPI с `MEDSI_STORAGE=postgres`.
- **Миграции:** PostgreSQL 18.6 с нуля до `0008_check_in_attempt`; отдельный апгрейд `0007 → 0008` с существующим синтетическим подтверждённым check-in сохранил редакции 1/1 и оставил `creation_key=NULL`. `alembic check` в обоих случаях без расхождений. `git diff --check` прошёл.
- **Вне проверки:** физический микрофон, качество распознавания и live GigaChat заново не принимались. Для браузера использован сохранённый синтетический WAV и реальный локальный ASR; нет новой оценки точности. Не выполнялись установка зависимостей с нуля, апгрейд реальных данных, длительная нагрузка и аудит research-v2. Research-v2 не менялся.
