# 4. Что пропущено

## P0 — блокирует демонстрацию или конкурс

### 4.1. Код не зафиксирован в Git

Требование: репозиторий должен содержать запускаемый проект.

Фактически `git status` показывает:

```text
?? backend/
?? experiments/
?? frontend/
?? docker-compose.yml
?? .env.example
?? AGENTS.md
?? alembic.ini
```

Единственный коммит `ec66a6b` содержит только `.gitignore`, README и техническую спецификацию. При клонировании `origin/main` исходного кода не будет.

Последствие: текущий проект нельзя считать поставленным или воспроизводимым.

Приоритет: **P0**.

### 4.2. Нет полноценного цикла событий и уведомлений

ТЗ требует `/trends`, `/events`, `/notifications`, временную шкалу и объяснение причин.

В [backend/app/main.py](/home/linuxoid/Projects/medsi-care/backend/app/main.py:325) анализ только возвращает временный `AnalysisResponse`. Результат не сохраняется.

Отсутствуют:

- `monitoring_events`;
- `notifications`;
- `/profiles/{id}/trends`;
- `/profiles/{id}/events`;
- `/notifications`;
- отметка уведомления прочитанным;
- история событий для caregiver.

Последствие: система не демонстрирует главный пользовательский результат — объяснимое уведомление.

Приоритет: **P0**.

### 4.3. Факты из дневника не участвуют в анализе

Domain-функция умеет учитывать `symptom_facts`, но endpoint анализа вызывает:

```python
event = analyze_observation(latest, baseline)
```

Факты не передаются: [backend/app/main.py](/home/linuxoid/Projects/medsi-care/backend/app/main.py:329).

Последствие: подтверждённая жалоба никогда не влияет на событие в приложении. Фактически multimodal monitoring отсутствует.

Приоритет: **P0**.

### 4.4. Нет интерфейса подтверждения фактов

Backend предоставляет extraction и confirmation endpoints, но `frontend/src/App.tsx`:

- не вызывает `/extract`;
- не показывает список фактов;
- не позволяет исправить категорию/polarity/evidence;
- не вызывает `/confirm`.

Пользовательский сценарий из ТЗ «голос → текст → исправление → подтверждение → мониторинг» не проходит полностью.

Приоритет: **P0**.

### 4.5. Нет графиков

В ТЗ графики являются обязательным P0. В frontend отображается только `<ul>` со списком измерений. В `package.json` нет Recharts, хотя библиотека указана в ТЗ.

Приоритет: **P0**.

### 4.6. Нет импорта демосценария

Требуется воспроизводимый сценарий на несколько недель. Генератор в `experiments/` не загружает данные в приложение.

Отсутствуют:

- `/demo/load-scenario`;
- seed-команда для PostgreSQL;
- подготовленные сценарии для демонстрации;
- скрипт очистки и повторной загрузки.

Последствие: демонстрация требует вручную вводить данные, а baseline нельзя быстро показать на подготовленной истории.

Приоритет: **P0**.

### 4.7. Нет аварийного safety-сценария

В ТЗ отдельно указан UC-04 для потенциально экстренных жалоб. В репозитории отсутствует `safety`-модуль, emergency-rule, тесты обхода правил и безопасная формулировка.

Приоритет: **P0**.

### 4.8. Валидация измерений неполная

`ObservationCreate` проверяет только тип, `allow_inf_nan=False`, enum показателя и строку unit: [backend/app/schemas.py](/home/linuxoid/Projects/medsi-care/backend/app/schemas.py:39).

Не проверяются:

- допустимые диапазоны;
- отрицательные сон/пульс/давление;
- будущая дата;
- слишком старая дата;
- дубликаты;
- качество измерения;
- согласованность с `source`.

Приоритет: **P0**, поскольку FR-05 прямо требует проверки значений и даты.

### 4.9. README не запускает чистое окружение надёжно

README создаёт `.venv` и устанавливает пакеты через `.venv/bin/pip`, но далее использует глобальные команды:

```bash
alembic upgrade head
```

Активации `.venv` нет. В текущей среде системный `pytest` отсутствует, хотя `.venv/bin/python -m pytest` работает.

Приоритет: **P0** для критерия запуска из чистого репозитория.

В [backend/app/main.py](/home/linuxoid/Projects/medsi-care/backend/app/main.py:192) наличие `corrected_text` само по себе считается подтверждением:

Исправление текста и подтверждение фактов должны быть разными состояниями.

Отсутствуют:

Это объясняет отсутствие части API и невозможность восстановить историю анализа.

### 4.14. Нет аудита действий

ТЗ требует журнал действий без медицинского содержимого. Нет записи:

- входа;
- создания измерения;
- подтверждения факта;

ТЗ требует защиту от несанкционированной массовой отправки и отдельные тесты обхода правил через пользовательский текст.

В проекте нет rate limit, request throttling или тестов prompt injection.

### 4.16. ASR ограничен размером, но не длительностью и форматом содержимого

`validate_audio_filename` проверяет расширение, но не MIME или содержимое файла: [backend/app/ai/asr.py](/home/linuxoid/Projects/medsi-care/backend/app/ai/asr.py:59).

Нет ограничения длительности аудио. Сжатый длинный файл может пройти ограничение 25 MB.

### 4.17. Нет резервного текстового режима для extraction

При отсутствии GigaChat ручные измерения продолжают работать, но извлечение фактов из текста недоступно. Это соответствует частичному отказоустойчивому режиму, но не полному offline-сценарию.

Ollama в MVP добавлять не следует согласно `AGENTS.md`; нужно либо явно зафиксировать это как deferred, либо реализовать маленький детерминированный fallback для ограниченного набора признаков.

### 4.18. Версии backend-зависимостей не зафиксированы

`pyproject.toml` использует диапазоны `>=,<`, но нет lock-файла Python-зависимостей. Это нарушает требование воспроизводимой сборки.

# 5. Ошибки архитектуры и технические риски

- Код физически организован как модульный монолит, но каталоговая структура не соответствует заявленной архитектуре: нет `api`, `services`, `monitoring`, `safety`.
- Global `store = build_store()` создаётся при импорте приложения. При неверном порядке миграций PostgreSQL startup может обратиться к отсутствующим таблицам.
- Health endpoint всегда возвращает `{"status": "ok"}` и не проверяет доступность PostgreSQL.
- Demo-аутентификация использует статические пароли и fallback-секрет по умолчанию. Для синтетической локальной демонстрации допустимо, но должно быть явно ограничено dev-режимом.
- Нет профиля владельца в модели БД (`user_id`, timezone, age_group).
- В observation отсутствует `quality`, хотя качество данных участвует в концепции PMAF.
- Версия алгоритма присутствует только в возвращаемом ответе, но не сохраняется вместе с событием.
- Нет идентификаторов исходных наблюдений и периода сравнения в событии.
- Нет журналирования производительности ASR и анализа.
- Нет frontend-тестов и Playwright-сценариев.
- `docker-compose.yml` поднимает только базу. Это не единый запуск приложения, а только инфраструктурная зависимость.
- README противоречит фактическому коду: в строках 7–9 указано, что GigaChat и faster-whisper пока не входят в срез, хотя adapters и endpoints уже добавлены.

## Критическая проблема эксперимента

В [experiments/methods.py](/home/linuxoid/Projects/medsi-care/experiments/methods.py:65) Method C использует:

```python
current.symptom_present
```

Это уже готовая синтетическая метка, а не результат извлечения из `symptom_text`, ASR или LLM.

Поэтому улучшение Method C измеряет эффект **оракульной метки симптома**, а не эффект реального мультимодального pipeline. Полученные F1 нельзя использовать как подтверждение работы текстового извлечения.

Нужно заменить прямой доступ к `symptom_present` на отдельный воспроизводимый extractor или заранее подготовленные структурированные факты, которые не раскрывают эталонную метку напрямую.

## Другие ограничения

- `train_ids` вычисляются, но не используются для настройки методов.
- Дополнительная абляция Method C без качества данных отсутствует.
- Нет latency от onset до события.
- Нет WER для речи.
- Нет качества extraction фактов.
- Нет доли некорректных объяснений.
- Нет confidence intervals.
- Нет графиков результатов.
- Сценарии содержат мало разновидностей жалоб.
- Нет отрицательных текстов с тревожными словами, которые не означают текущий симптом.
- Нет постепенных изменений и редких ошибочных значений в нужной полноте.
- В `missing_change` целевая метка может быть положительной при отсутствии наблюдаемого сигнала, что требует отдельного описания как сценария недоступных данных.

Вывод: экспериментальный каркас есть, но сейчас его результаты нельзя включать в конкурсную работу как доказательство превосходства реального Method C.

# 10. Решение для основного Codex

Следующим сообщением следует разрешить работу только над P0:

- `backend/app/main.py`;
- `backend/app/schemas.py`;
- `backend/app/domain/monitoring.py`;
- новые модели и миграции для events/notifications/audit;
- `backend/app/safety/`;
- `experiments/`;
- `frontend/src/`;
- `README.md`, `.env.example`, `docker-compose.yml`;
- backend/frontend integration tests.

Пока не трогать:

- реальные медицинские данные;
- FHIR и интеграцию с МИС;
- настоящие wearable API;
- TTS;
- сложные приглашения;
- дополнительные LLM-провайдеры;
- production-аутентификацию;
- Ollama как обязательную зависимость MVP.

Разработчику нужно утвердить:

- минимальный набор safety-жалоб и формулировки предупреждений;
- схему событий и уведомлений;
- правила объединения числового отклонения и подтверждённых фактов;
- формат demo-сценария;
- допустимый offline fallback для текстовых признаков;
- какие результаты эксперимента допустимо публиковать как инженерные, а какие следует исключить.
