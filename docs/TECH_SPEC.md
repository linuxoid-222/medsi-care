## 1. Концепция проекта

**MEDSI Care** — исследовательский программный прототип мультимодального ИИ-ассистента, предназначенного для регулярного сбора информации о самочувствии пожилого человека, анализа индивидуальной динамики показателей и формирования объяснимых уведомлений об изменениях, заслуживающих внимания.

Система объединяет три источника:

- **Голос:** ответы пользователя на вопросы о самочувствии, преобразованные в текст с помощью распознавания речи.
- **Текст:** сообщения и структурированные записи о самочувствии.
- **Числовые данные:** сон, активность, пульс, давление из ручного ввода или симулятора устройств.

Принцип работы — не постановка диагноза, а выявление изменений относительно собственной истории человека с учётом субъективных жалоб и качества доступных данных.

**Основной результат проекта:** работающий веб-прототип, который воспроизводит полный цикл мониторинга и демонстрирует сравнительное экспериментальное исследование алгоритмов обнаружения отклонений.

### 1.1. Проблема

Традиционные цифровые дневники здоровья преимущественно показывают отдельные показатели и их историю. Для пожилых пользователей это создаёт несколько затруднений:

1. Необходимость самостоятельно регулярно вводить данные.
2. Сложность интерпретации динамики показателей.
3. Отсутствие единого представления о числовых измерениях и субъективном самочувствии.
4. Необходимость родственникам самостоятельно просматривать историю наблюдений.
5. Вероятность избыточных уведомлений при использовании примитивных универсальных порогов.

### 1.2. Цель

Разработать и экспериментально оценить программный прототип, способный объединять разнородные данные домашнего наблюдения и объяснимо обнаруживать заранее определённые изменения в состоянии пожилого человека.

### 1.3. Задачи

- Разработать интерфейс голосового и текстового взаимодействия.
- Реализовать сбор и хранение показателей.
- Создать систему персональных базовых уровней.
- Разработать алгоритм объединения признаков.
- Реализовать прозрачные уведомления.
- Создать интерфейс доверенного родственника.
- Сформировать синтетический набор тестовых историй.
- Провести сравнительные эксперименты.
- Подготовить конкурсную работу, презентацию и демонстрацию.

### 1.4. Ограничения назначения

На этапе конкурса MEDSI Care:

- не устанавливает заболевания;
- не назначает лечение и не корректирует лекарства;
- не оценивает достоверную вероятность конкретного заболевания;
- не заменяет врача или экстренную медицинскую помощь;
- не заявляет доказанную клиническую эффективность;
- не используется для реального клинического принятия решений.

Прототип работает на синтетических данных и предназначен для оценки технической концепции.

## 2. Пользователи и сценарии

### 2.1. Роли

| Роль                     | Назначение                                                                    |
| ------------------------ | ----------------------------------------------------------------------------- |
| Пожилой пользователь     | Общается с ассистентом, вводит показатели и просматривает собственную историю |
| Доверенное лицо          | С разрешения пользователя просматривает динамику и уведомления                |
| Разработчик/демонстратор | Запускает подготовленные сценарии и экспериментальные тесты                   |

Функциональность врача или оператора клиники не входит в MVP.

### 2.2. Сценарий UC-01. Ежедневная проверка самочувствия

1. Пользователь открывает приложение.
2. Ассистент предлагает рассказать о самочувствии.
3. Пользователь записывает короткое голосовое сообщение или вводит текст.
4. Система распознаёт речь.
5. Модель выделяет структурированные жалобы и признаки.
6. Пользователь может проверить и исправить распознанную информацию.
7. Подтверждённая запись сохраняется в истории.
8. Система анализирует изменения с учётом накопленных данных.
9. Пользователь получает понятное объяснение результата.

### 2.3. Сценарий UC-02. Обнаружение изменения

1. В систему поступают ежедневные измерения.
2. Алгоритм проверяет полноту и достоверность данных.
3. Показатели сравниваются с персональным базовым уровнем.
4. Из ответов пользователя извлекается информация о самочувствии.
5. Движок правил обнаруживает заранее заданное сочетание изменений.
6. Формируется событие мониторинга с указанием исходных данных и причин срабатывания.
7. Доверенное лицо видит уведомление в своей панели.

### 2.4. Сценарий UC-03. Недостаток данных

Если наблюдений недостаточно, система не должна создавать видимость уверенного медицинского заключения.

Вместо этого она сообщает, например: «Пока недостаточно записей, чтобы сравнить показатели с вашим обычным уровнем».

### 2.5. Сценарий UC-04. Потенциально экстренная жалоба

Если пользователь сообщает о симптомах, которые могут требовать срочной медицинской оценки, приложение не должно продолжать обычную успокаивающую беседу.

Должен срабатывать отдельный консервативный сценарий безопасности с предложением незамедлительно обратиться за экстренной помощью. Он не должен зависеть исключительно от решения LLM. Набор таких сценариев и формулировки требуют дальнейшего согласования с медицинским специалистом перед каким-либо реальным использованием.

## 4. Технологический стек

Для индивидуальной разработки выбран модульный монолит: он проще в сборке и тестировании, чем набор независимых микросервисов.

| Уровень                    | Решение                                         |
| -------------------------- | ----------------------------------------------- |
| Frontend                   | React, TypeScript, Vite                         |
| UI                         | Tailwind CSS и доступные компонентные примитивы |
| Backend                    | Python, FastAPI                                 |
| ORM и миграции             | SQLAlchemy, Alembic                             |
| Хранение                   | PostgreSQL                                      |
| Вычисления                 | NumPy, Pandas                                   |
| Валидация                  | Pydantic                                        |
| Распознавание речи         | faster-whisper                                  |
| Диалог и извлечение фактов | LLM через отдельный адаптер                     |
| Локальный LLM-вариант      | Ollama с компактной совместимой моделью         |
| Графики                    | Recharts                                        |
| Контейнеризация            | Docker Compose                                  |
| Тестирование               | pytest, Playwright                              |
| Разработка                 | Codex, GitHub                                   |

Использование внешнего LLM API допускается только в конфигурации с обезличенными/синтетическими данными и отдельно контролируемыми расходами. ChatGPT Plus не предоставляет API-квоту для самого приложения.

### 4.1. Принцип архитектуры

Весь продукт состоит из пяти основных логических блоков:

1. Presentation — пользовательские интерфейсы.
2. Application — API, авторизация и бизнес-операции.
3. Data — база наблюдений и пользовательские профили.
4. AI — распознавание речи и обработка текста.
5. Monitoring — персональные базовые уровни, правила, объяснения и события.

В MVP они находятся в одном backend-приложении с чёткими границами модулей. Модели распознавания речи и LLM взаимодействуют через адаптеры.
Для синтетической демоверсии используется минимальный подписанный bearer-токен
с ролями пользователя и доверенного лица. Доверенное лицо имеет read-only
доступ к разрешённому summary; production-аутентификация и приглашения не входят
в текущий срез.

### 4.2. Потоки данных

**Голос:** запись → проверка формата → распознавание → подтверждение пользователем → извлечение признаков → структурированная запись.

**Измерения:** ручной ввод/симулятор → валидация → база данных → аналитика базового уровня.

**Обнаружение:** валидные измерения + подтверждённые признаки самочувствия → движок мониторинга → события с доказательствами → панель пользователя и доверенного лица.

**Генерация объяснений:** набор проверенных признаков → ограниченный текстовый шаблон либо LLM-перефразирование → проверка допустимого содержания → интерфейс.

LLM не имеет права создавать измерения, которые отсутствуют в исходных данных.

### 4.3. Техническая валидация и safety MVP

Сервер отклоняет измерения, нарушающие технические ограничения прототипа:

| Показатель | Допустимый технический диапазон | Единица |
| --- | ---: | --- |
| `sleep_hours` | 0–24 | `hours` |
| `activity_minutes` | 0–1440 | `minutes` |
| `pulse_bpm` | 20–250 | `bpm` |
| `systolic_bp` | 50–250 | `mmHg` |
| `diastolic_bp` | 30–150 | `mmHg` |

Это инженерные границы для синтетического демо, а не медицинские нормы. Для
одного момента систолическое давление должно быть больше диастолического.
Будущая дата, неизвестный `source` (`manual` или `simulator`) и неизвестный
`quality` (`unknown`, `good` или `questionable`) отклоняются как HTTP 422.

Модуль `backend/app/safety/rules.py` версии `safety-v1` проверяет только
подтверждённые пользователем факты категорий `chest_pain`,
`shortness_of_breath`, `loss_of_consciousness`, `stroke_signs` и
`severe_bleeding`. Он не читает неподтверждённый текст и не вызывает LLM.
Срабатывание сохраняется как событие уровня `safety` с `rule_version` и
`evidence`, создаёт notification доверенному лицу и показывает рекомендацию
обратиться за срочной медицинской помощью. Диагнозы и назначения отсутствуют.

### 6.2. Инварианты данных

- Каждое наблюдение принадлежит ровно одному профилю.
- Время измерения сохраняется в UTC, интерфейс использует часовой пояс профиля.
- Для числовых данных обязательно указывается единица измерения.
- В системе различаются фактические записи пользователя, данные симулятора и вычисленные признаки.
- В данных сохраняется источник и версия алгоритма обработки.
- Пропуски не заменяются нулями.
- Удаление и отзыв доступа обрабатываются отдельно от изменения пользовательских ролей.
- Прямой запрос к профилю без соответствующего разрешения отклоняется сервером.

### 6.3. Подготовка к интеграции

Внутренняя модель наблюдений может быть сопоставлена с HL7 FHIR `Observation`, однако реализация полноценного FHIR-сервера и совместимость с информационными системами МЕДСИ **не входят в MVP**.

## 7. Алгоритм превентивного мониторинга

Это центральный исследовательский компонент MEDSI Care.

### 7.1. Подход

Предлагается экспериментальный метод **PMAF — Personalized Multimodal Attention Fusion** (рабочее название).

Он объединяет:

1. Персональную динамику числовых показателей.
2. Структурированные признаки из голосовых и текстовых жалоб.
3. Полноту и качество данных.
4. Правила формирования объяснимых событий.

Название — обозначение собственного проектного подхода, а не утверждение о существовании нового общепризнанного научного метода.

### 7.2. Индивидуальная норма

Для каждого показателя вычисляются устойчивые характеристики предшествующей истории наблюдений.

Предлагаемый протокол:

- 14 предыдущих календарных дней для построения базового уровня.
- Не менее 7 валидных дневных наблюдений.
- Последние 1–3 дня для анализа текущего изменения.
- При недостатке информации — статус «базовый уровень не сформирован».

Основной оценкой центра является медиана, а устойчивой мерой разброса — MAD (median absolute deviation).

Нормированное отклонение:

`z = (x − median) / (1.4826 × MAD)`

Если MAD равен нулю или слишком мал, применяется заранее определённая альтернативная оценка масштаба, основанная на допустимых для конкретного показателя параметрах. Алгоритм не должен создавать бесконечные оценки или делить на ноль.

Знак отклонения учитывается: например, для продолжительности сна и ежедневной активности существенным может быть именно снижение относительно привычного уровня. Для других показателей правила определяются отдельно.

**Важно:** коэффициенты, окна и пороги на данном этапе являются исследовательскими гиперпараметрами. Они не являются медицинскими нормами и не утверждаются как клинически валидированные.

Продуктовая реализация после F1/F5/F10: `daily-multimetric-v2`.
Анализ выполняется для всех пяти метрик за текущий локальный день до `as_of`
(по умолчанию серверное now UTC); часовой пояс хранится в `profiles.timezone`.
Baseline: 14 предыдущих локальных дат, минимум 7 различных валидных дней,
текущий день целиком исключён. Сон/активность: последнее суточное значение,
при совпадении timestamp — медиана ties; пульс/давление: дневная медиана.
Повторные суточные значения не суммируются. Будущие/невалидные/questionable
измерения исключаются. Unknown допускается, но явно отмечается.

Отсутствующее измерение, недостаточный baseline и отсутствие отклонения имеют
разные per-metric статусы. Attention любой метрики сохраняет общий attention,
даже если другой метрике недостаёт истории. Подробный контракт, приоритеты
объединения, границы периода и ограничения — `docs/MONITORING.md`.
Это изменение продуктового кода, не зафиксированного эксперимента research-v2.

### 7.3. Извлечение признаков

ИИ-компонент превращает текст самочувствия в структурированный объект, содержащий:

- категорию упомянутого симптома;
- наличие, отсутствие или неопределённость признака;
- временной контекст;
- дословное подтверждающее выражение;
- уверенность обработки;
- необходимость подтверждения пользователем.

При неясном ответе ассистент может задать один уточняющий вопрос.

Отсутствие упоминания симптома **не означает**, что симптом отсутствует.

### 7.4. Объединение признаков

Движок получает:

- нормированные отклонения;
- признаки жалоб;
- показатели качества данных;
- предшествующие события;
- версию конфигурации правил.

Результат определяется детерминированными правилами. На первом этапе используются три состояния:

- Нет выявленных изменений по проверяемым правилам.
- Обнаружено изменение, заслуживающее внимания.
- Недостаточно данных или требуется дополнительная проверка.

Потенциально экстренные жалобы обрабатываются отдельно, а не по суммарному баллу.

Если используется вспомогательный балл 0–100, он должен называться «индексом внимания», а не вероятностью заболевания. Его веса необходимо публиковать в конфигурации эксперимента и проверять на отложенном наборе сценариев.

### 7.5. Объяснимость

Каждое событие сохраняет:

- идентификаторы исходных наблюдений;
- период сравнения;
- величину обнаруженных изменений;
- подтверждённые признаки самочувствия;
- список сработавших правил;
- качество и полноту данных;
- версию алгоритма.

Пример объяснения:

«В течение трёх последних дней продолжительность сна была ниже привычного уровня. Также в сегодняшней записи пользователь сообщил о слабости. Система рекомендует уточнить самочувствие».

Такие сообщения не должны содержать выводов о конкретных заболеваниях.

## 8. ИИ-компоненты

### 8.1. Распознавание речи

Ввод: русскоязычное аудио ограниченной длительности.

Вывод: текст, служебные метаданные и статус распознавания.

В MVP используется локальный faster-whisper. Аудиофайл проверяется по размеру
и расширению, обрабатывается через временный файл и не сохраняется после
завершения транскрипции. Результат имеет статус `awaiting_review`: пользователь
должен проверить и при необходимости исправить текст до извлечения фактов.
Транскриптор не создаёт жалобы и события мониторинга самостоятельно.

Ошибки аудиофайла, отсутствие речи или недостаточная уверенность не должны приводить к автоматическому созданию жалоб.

Перед сохранением структурированных признаков пользователь видит распознанный текст и может его исправить.

### 8.2. Обработка естественного языка

Основной провайдер MVP — GigaChat API через узкий backend-адаптер. LLM используется для:

- анализа ответов на заранее подготовленные вопросы;
- извлечения признаков в заданную JSON-схему;
- формулирования уточняющих вопросов;
- создания понятного объяснения на основе проверенных фактов.

Выход LLM проходит проверку Pydantic и бизнес-валидаторов.

Не прошедшие валидацию ответы не записываются как факты.

Извлечённые факты сначала возвращаются со статусом `awaiting_confirmation`.
Они не сохраняются и не участвуют в мониторинге до подтверждения пользователем.
Для структурированного ответа используется JSON Schema, а затем проверяется
наличие каждого доказательства в исходном тексте.

В первом экспериментальном контракте LLM возвращает минимальный набор полей
`category`, `polarity`, `evidence`. Временной контекст и confidence не считаются
надёжными до подтверждения пользователем и заполняются отдельным шагом.

После подтверждения endpoint `/check-ins/{checkin_id}/confirm` повторно проверяет
доказательства относительно подтверждённого текста и сохраняет факты в
`symptom_facts`. Повторное подтверждение заменяет набор фактов этого check-in;
неподтверждённый ответ провайдера не записывается.

После F2/F3/F9 (2026-11-10): PATCH/confirm требуют `text_revision`. Изменение
эффективного текста повышает revision и сбрасывает прежнюю проверку/активные
факты; сохранение того же текста не сбрасывает её. Extraction возвращает revision;
устаревший extraction/confirm получает 409. Пустое `facts: []` сохраняется как
проверенный результат через отдельные `confirmed_revision`/`confirmed_at`.
GET одной записи, список и caregiver summary возвращают единый status и facts.

Обычный monitoring отбирает текущие подтверждённые факты из UTC-окна
`[as_of − 24h, as_of]` по created_at записи, с confirmed_at не позже as_of.
Новое absent/uncertain той же категории подавляет более старое present;
отсутствие упоминания/пустой набор не означает отрицание. Это инженерное
правило, не медицинский норматив. Safety-события имеют отдельный жизненный цикл.
Новые события сохраняют независимый `text_provenance` с IDs, revision, цитатой,
category/polarity, временем и версией правил. Миграция `0006_fact_lifecycle`.
Полный контракт, разрешение конфликтов и legacy-ограничения: `docs/FACTS.md`.
Продуктовая комбинированная версия — `daily-multimetric-v2+facts-window-v1`;
числовые правила и frozen research-v2 не изменяются.

### 8.3. Граница ответственности

LLM **не должна**:

- напрямую выполнять SQL-запросы;
- произвольно изменять показатели;
- назначать лекарства;
- создавать или подтверждать диагноз;
- выбирать новые медицинские пороги;
- отправлять уведомления без прохождения движка правил;
- передавать исходные медицинские сведения неизвестным внешним сервисам.

### 8.4. Отказоустойчивость

При недоступности LLM:

- ручной ввод показателей продолжает работать;
- детерминированный анализ сохраняется;
- пользователь видит сообщение о временной недоступности голосового анализа;
- система не подменяет отсутствующий ИИ-результат выдуманным.

## 11. Безопасность и приватность

Сведения о здоровье относятся к специальным категориям персональных данных. Реальная эксплуатация требует самостоятельного правового и информационно-безопасностного проектирования.

Для конкурсного прототипа устанавливаются следующие правила:

1. По умолчанию применяются синтетические профили и измерения.
2. Настоящие медицинские документы и записи пользователей не собираются.
3. Тестовые данные явно помечаются как синтетические.
4. Учитываются роли и разрешения на доступ.
5. Секреты хранятся вне Git.
6. В логах отсутствуют тексты медицинских жалоб, аудио и токены авторизации.
7. Аудиозаписи удаляются после обработки, если пользователь не дал отдельного разрешения на их хранение.
8. Пользовательские вводы не включаются без разрешения в обучающие датасеты.
9. Предусмотрены проверка некорректных значений и защита от несанкционированной массовой отправки запросов.
10. Отдельно тестируются попытки обойти правила посредством инструкций внутри пользовательских сообщений.

Для реального внедрения дополнительно необходимо оценить юридическое основание обработки данных, требования к их размещению, порядок получения согласий, возможность отзыва согласия и возможную классификацию ПО как медицинского изделия.

Надпись «не является медицинским изделием» сама по себе не освобождает программный продукт от применимых требований.

## 12. Исследовательская составляющая

### 12.1. Исследовательский вопрос

Улучшает ли объединение структурированных жалоб и персональной динамики количественных показателей обнаружение заранее определённых изменений по сравнению с анализом только числовых наблюдений?

### 12.2. Проверяемая гипотеза

На заранее созданном и отложенном наборе синтетических сценариев предложенный мультимодальный алгоритм покажет лучшие показатели обнаружения заданных отклонений, чем выбранные базовые методы, при контролируемом количестве ложных уведомлений.

Это **гипотеза**, а не заранее доказанный результат.

### 12.3. Сравниваемые методы

- **Baseline A:** фиксированные экспериментальные пороги для числовых показателей.
- **Baseline B:** персональные статистические отклонения без текстовых признаков.
- **Method C:** персональные статистические отклонения и структурированные
  текстовые признаки, полученные независимым extractor, с учётом качества и
  полноты данных.

Дополнительная абляция — Method C без текстовых признаков. Воспроизводимый
протокол имеет версию `research-v2`; deterministic extractor является
инженерной эвристикой и не является клинически обученной моделью.

Все методы должны обрабатываться на одном и том же отложенном наборе тестовых
историй. Разделение выполняется по `profile_id` с фиксированным seed, профили
train и test не пересекаются, а train в текущем протоколе не используется для
подстройки тестового результата.

В репозитории воспроизводимый запуск реализован командой:

```bash
PYTHONPATH=. python -m experiments.run_experiment --output experiments/results/latest.json
```

Конфигурация по умолчанию — 100 профилей, 28 дней, seed 42 и разделение 80/20
по профилям. Результат сохраняет конфигурацию, split, версии правил и extractor.
Полученные метрики являются результатом синтетического сценария и не трактуются
как клиническая эффективность.

Проверенный артефакт: `experiments/artifacts/research-v2-seed42-2026-11-10/`.
Схема отчёта `research-report-v2.1` дополнительно сохраняет TN, знаменатели,
количество необнаруженных эпизодов, исходные test-записи и предсказания.
Подробные определения и графики приведены в `docs/RESEARCH.md`.
Пороги и генератор после просмотра held-out не изменялись.

### 12.4. Синтетические данные

Рекомендуемая стартовая конфигурация:

- 100 сгенерированных профилей.
- 28 дней наблюдений на профиль.
- Различающиеся индивидуальные уровни сна, активности и пульса.
- Стабильные периоды.
- Кратковременные и постепенные изменения.
- Пропуски измерений.
- Шум и редкие ошибочные значения.
- Жалобы, согласующиеся и не согласующиеся с числовой динамикой.
- Негативные сценарии, где тревожные слова не означают текущую жалобу.

Метки событий и фактов задаются независимой спецификацией сценариев и хранятся
как `ground_truth_event`, `ground_truth_facts`, `scenario_type` и
`change_start_day`. Эти labels используются только evaluator. Запрещается
передавать их в extractor, prompt LLM, monitoring engine, Method C или frontend,
а также определять эталонную метку повторением логики проверяемого алгоритма.

Данные делятся по профилям, чтобы сведения одного профиля не попадали
одновременно в train и финальное тестирование. Method C использует только
числовую историю, текущий check-in/corrected_text, валидированный результат
extractor, quality и completeness.

### 12.5. Метрики

Основные:

- Precision.
- Recall.
- F1-score.
- Количество ложных уведомлений на 100 человеко-дней.
- Доля сценариев, получивших статус «недостаточно данных».

Дополнительные:

- Время от начала заданного изменения до события мониторинга.
- Качество извлечения симптомов по размеченным сообщениям.
- Precision/Recall/F1 структурированных фактов extractor.
- Ошибки отрицания и неопределённости extractor.
- Точность распознавания речи (WER).
- Доля некорректных объяснений и неподтверждённых фактов.
- Время выполнения анализа.

Для метрик указываются количество сценариев, числители и знаменатели, ограничения, а при возможности — интервалы неопределённости.

В текущем research-v2 единица основной оценки — человеко-день: 560 дней
20 held-out профилей (156 положительных и 404 отрицательных). TP/FP/FN/TN
включают insufficient_data как отсутствие срабатывания; такие дни не исключаются.
Ложные дни срабатывания на 100 человеко-дней = FP/560 × 100, повторы по дням
не подавляются. Это не количество объединённых уведомлений продукта.
Задержка — средняя разница индексов дней от начала эпизода до первого
срабатывания только среди обнаруженных эпизодов; пропуски считаются отдельно.

Оценка описательная: 20 test-профилей, один seed; доверительные интервалы не
рассчитаны, статистическая устойчивость улучшения не установлена. Все текстовые
шаблоны test встречаются в train; held-out профиль не означает held-out язык.
В test нет uncertain-фактов, поэтому их ошибки не являются оценкой качества.

### 12.6. Предварительные целевые критерии

Это инженерные ориентиры, а не обещанные научные результаты:

- 100% прохождение заранее определённых тестов контроля доступа.
- 100% прохождение критических сценариев безопасности из тестового набора.
- Отсутствие выдуманных измерений в наборе проверочных объяснений.
- Воспроизводимость эксперимента с фиксированным seed.
- Улучшение F1 относительно Baseline B — проверяемая цель, а не условие сокрытия отрицательного результата.

Даже отсутствие улучшения должно быть отражено честно, с анализом причин.

### 12.7. Ограничения результатов

Тестирование на синтетических данных не доказывает:

- клиническую чувствительность;
- предотвращение заболеваний;
- снижение смертности или госпитализаций;
- эффективность на реальных пожилых пациентах;
- безопасность для медицинского применения.

Такие заявления требуют иной исследовательской и нормативной процедуры.

## 13. Новизна и позиционирование

Заявляемая новизна формулируется как **проверяемое инженерно-исследовательское предложение**, а не как изобретение первой в мире системы такого типа.

Предлагаемые отличительные свойства:

1. Объединение личной истории числовых показателей с подтверждёнными сведениями из естественной речи.
2. Явный учёт недостатка данных и неопределённости.
3. Объяснение каждого события через конкретные исходные наблюдения.
4. Отделение разговорной языковой модели от алгоритма принятия решения.
5. Экспериментальное сравнение способов объединения данных с возможностью воспроизводимости.

### 13.1. Предварительные аналоги

**ElliQ:** голосовой ИИ-компаньон для пожилых людей с функциями коммуникации, напоминаний и взаимодействия с близкими.

**СберЗдоровье:** дистанционный мониторинг измерений, включая давление, в связке с медицинским наблюдением.

**Medsenger:** российская платформа сопровождения пациентов с опросниками, дневниками и медицинским взаимодействием.

**Сеченовский Университет:** проекты дистанционного сопровождения пациентов, включающие голосового ИИ-помощника.

Следовательно, сама идея голосового общения, мониторинга или уведомления родственников не является уникальной.

Конкурсное преимущество MEDSI Care нужно доказывать именно реализацией и результатами сравнения выбранного способа объединения признаков.

## 15. Организация разработки с Codex

### 15.1. Принципы

Codex выполняет задачи по утверждённой спецификации; автор проекта самостоятельно принимает архитектурные решения и проверяет результат.

Разработка ведётся короткими итерациями с проверкой тестов после каждого завершённого функционального блока.

### 15.2. Рекомендуемые документы

- `docs/PRODUCT.md` — концепция и сценарии.
- `docs/TECH_SPEC.md` — функциональные требования.
- `docs/ARCHITECTURE.md` — компоненты, контракты и потоки.
- `docs/RESEARCH.md` — гипотеза, методы и метрики.
- `docs/SAFETY.md` — ограничения безопасности.
- `docs/ROADMAP.md` — график и контрольные точки.
- `AGENTS.md` — правила исполнения задач.

### 15.3. Правила для Codex

- Сначала читать актуальные документы проекта.
- Не добавлять функции вне текущего этапа.
- Не менять схемы API без обновления спецификации.
- Каждое изменение критической логики сопровождать тестами.
- Не подменять работающую интеграцию декоративной имитацией.
- Все демоданные явно маркировать.
- Не заявлять клинических результатов.
- Не добавлять секреты в репозиторий.
- После каждого этапа предоставлять список изменений, команды запуска, результаты тестов и известные ограничения.

### 15.4. Стратегия Git

Для индивидуального проекта достаточно `main` и короткоживущих веток `feature/*`, `fix/*`, `research/*`.

После завершения задачи:

1. Код проходит локальные проверки.
2. Codex создаёт описание изменений.
3. Разработчик проверяет diff.
4. Изменения объединяются с `main`.
5. Обновляется журнал прогресса.

Не следует создавать сложную систему самостоятельных агентов и параллельных ветвей только ради использования ИИ.

## 18. Критерии готовности к подаче

MVP считается завершённым, если:

- [ ] Репозиторий содержит документированные команды запуска.
- [ ] Приложение запускается из чистого окружения.
- [ ] Доступны обе пользовательские роли.
- [ ] Можно ввести и просмотреть показатели.
- [ ] Можно записать голосовое сообщение и получить транскрипт.
- [ ] Можно подтвердить извлечённые признаки.
- [ ] Работает индивидуальный базовый уровень.
- [ ] Реализован воспроизводимый движок событий.
- [ ] Каждое событие имеет объяснимые основания.
- [ ] Проводится сравнительный эксперимент.
- [ ] Результаты эксперимента сохранены и воспроизводимы.
- [ ] Есть тесты ошибок и безопасности.
- [ ] Есть готовая демонстрация полного сценария.
- [ ] Описаны ограничения.
- [ ] Подготовлены конкурсная работа и презентация.
- [ ] Проверен полный комплект заявки.

**Главный критерий успеха:** работающая, объяснимая и экспериментально проверенная система, в которой действительно объединяются разные источники информации, а не чат-бот с декоративными графиками.
