# Идемпотентность событий и права анализа

Блок независимого аудита F4/F6/F7/F8, 10 ноября 2026 года.
Продуктовый код; frozen research-v2, его данные, split и метрики не меняются.

## Анализ и значимые входы (F7)

`POST /api/v1/profiles/{id}/analysis` сохраняет результат и требует право записи.
Повтор возвращает **тот же event_id и первоначальный сохранённый snapshot**.
GET summary вычисляет доступный preview без сохранения (`event_id=null`);
GET events читает исторические snapshots.

Период дедупликации обычного анализа — календарный день профиля, начинающийся
в `period_start`, с его timezone. UTC-cutoff по-прежнему ограничивает числовые
входы и актуальные подтверждённые факты. Новые данные в течение дня могут менять
результат. Само продвижение часов запроса не создаёт новый результат при тех же
значимых входах. При совпадении ключа ответ содержит cutoff **первого сохранённого
события**, включая запросы разных as_of внутри одного дня с одинаковыми входами.
Новый календарный день — другой период; это также верно для insufficient_data.

Ключ `event-identity-v1` — SHA-256 канонического JSON:

- profile ID, вид события и версия правил;
- начало периода; для обычного анализа также timezone и локальные даты;
- статус/уровень, per-metric числовые результаты, baseline и его дневная история,
  качество, исходные/исключённые observation IDs;
- выбранные текстовые факты: check-in ID, text_revision, facts_revision,
  category/polarity, evidence, temporal_context, recorded_at и разрешение конфликта.

Ключ не содержит случайный ID нового события, HTTP request ID, created_at
события, меняющийся cutoff запроса или время повторного подтверждения.
Persisted observation/check-in IDs идентифицируют реальные входные записи,
а не попытки анализа. Новое сохранённое измерение является новым входом даже
при равном значении: его происхождение и набор source IDs изменились.
Списки фактов/evidence/source IDs канонизируются; порядок отправки фактов
не создаёт новое подтверждение. Числовые правила и пороги не изменены.

Если актуальные факты исчезают по 24-часовому окну или новое отрицание меняет
их выбор, ключ изменяется. Новая meaningful confirmation revision также меняет
его. Возврат к прежнему набору после изменения A→B→A имеет новую facts_revision.
Если точное состояние входов уже сохранялось в этом дне, возвращается его
существующий snapshot: по одной записи на идентичность, без повторной рассылки.
Это дедупликация результатов, а не клиническая модель продолжающихся эпизодов.

## Подтверждение и safety

`check_ins.facts_revision` — счётчик содержательных подтверждений, начиная с 0.
Он увеличивается только при новом подтверждении текущей редакции или изменении
набора фактов. Сравниваются unordered category, polarity, evidence,
temporal_context и confidence. При одинаковом наборе и уже подтверждённом тексте
операция не меняет fact IDs, confirmed_at, facts_revision и состояние проверки.
Пустое подтверждение тоже идемпотентно. Чтобы изменить текст, используется PATCH;
возврат к тому же тексту после реальной правки имеет новую text_revision.

Safety-ключ содержит версию safety-правил и snapshot подтверждённых trigger-фактов
с check-in/text/facts revision. Повтор этой же проверки возвращает прежний event
и не создаёт уведомлений. Другой check-in, новая редакция текста либо новое
содержательное подтверждение может создать новое safety-событие. Это техническая
идентичность явного подтверждения, не определение медицинского эпизода.

Изменение/отрицание/истечение обычных фактов не закрывает историческое safety
событие. Оно остаётся со своими первоначальными цитатами и IDs. Автоматического
закрытия и клинической классификации эпизодов нет.

В PostgreSQL подтверждение сериализуется `SELECT FOR UPDATE` по check-in;
UPDATE дополнительно проверяет text/facts revision. SQLite вместо отсутствующего
row lock использует `BEGIN IMMEDIATE` для подтверждения. В памяти — RLock.
Повтор того же содержимого возвращает сохранённый набор без обновления времени.

## SQL-гарантии и уведомления

Миграция `0007_event_identity` добавляет facts_revision и nullable identity_key,
а также уникальный индекс `uq_monitoring_events_identity_key`.

Repository сначала вставляет событие, затем в **одной транзакции** его два
локальных demo-уведомления. Уникальный индекс разрешает гонку одинаковых вставок
между независимыми процессами/соединениями. Только победитель создаёт уведомления.
Проигравший откатывает транзакцию и читает существующее событие; прочие ошибки
ограничений не скрываются. Проверка «найти перед вставкой» не является защитой.
При ошибке записи notification событие тоже откатывается. Повтор после сбоя
может завершить операцию; одно событие без его уведомлений не остаётся.

Повторы не обновляют существующие notifications, status и read_at сохраняются.
В памяти check+insert и уведомления защищены одним RLock. Reset удаляет события
вместе с ключами и уведомлениями; повторная загрузка/анализ снова возможны.

События до 0007 не переписываются и не удаляются: identity_key остаётся NULL.
Ретроспективная дедупликация старых уведомлений не выполняется. Первый новый
анализ после обновления может создать snapshot рядом с legacy-событием;
последующие одинаковые запросы используют новый ключ. Существующие проверки
и read_at при миграции сохраняются; facts_revision известных legacy-проверок — 0.

## Права caregiver (F6)

POST analysis проверяет `write=True` **до** анализа и любых записей. Caregiver
получает 403 без изменений events, notifications, observations, check-ins/facts.
Проверены также запреты demo-loader/reset, создания измерений/check-in,
редактирования, extraction, confirmation и ASR. Права проверяет backend.

Caregiver сохраняет чтение профиля, observations/check-ins, trends, events,
summary и собственных notifications. GET не создают события/уведомления.
Отметить собственное уведомление прочитанным можно; чужой notification/read
возвращает 404 и не меняет его состояние. Production auth/invitations не добавлены.

## Пустые значения и ручные факты (F4/F8)

Frontend до Number проверяет trim пустого ввода, затем Number.isFinite.
При пустоте/пробелах показывает ошибку и не отправляет запрос. Поле текстовое
с inputMode=decimal, чтобы пробелы можно было явно обработать. Введённый 0 остаётся
измерением для допускающих его сна/активности. Диапазоны, units и 422 на сервере
сохранены; пропуски не превращаются в ноль.

В разделе проверки доступен «Ручной ввод фактов (без LLM)»: выбор категории,
present/absent/uncertain, цитата из текущего сохранённого текста. Категории UI:
weakness, sleep_problem, cough и пять категорий safety-v1. Добавление создаёт
только локальный черновик. Явное подтверждение вызывает прежний API с текущей
text_revision, Pydantic/evidence-валидацией, правами и provenance. Автоматическое
подтверждение при ошибке extraction отсутствует. Невалидная цитата отклоняется;
редактирование текста требует сохранения и новой проверки. Ручное содержание
также требует осторожной проверки пользователем; совпадение цитаты не доказывает
клиническую корректность выбранной категории.

## Создание check-in после потери ответа

`POST /api/v1/profiles/{id}/check-ins` принимает необязательный заголовок
`Idempotency-Key` с UUID. UI генерирует его один раз для попытки сохранения
текущего транскрипта. При ошибке или недоставленном ответе повтор использует тот
же UUID. Успешное сохранение блокирует кнопку для этого транскрипта. Новая
запись аудио получает новый ключ, даже если распознанный текст совпал.

Миграция `0008_check_in_attempt` добавляет уникальный индекс по профилю и
ключу. PostgreSQL выбирает одну вставку при конкурентных повторах. Повтор с тем
же исходным текстом и source возвращает 201 и текущее состояние исходного
check-in с тем же ID. Текст сравнивается после API-нормализации пробелов по
краям. Тот же ключ с другим содержимым возвращает 409. Запрос без заголовка
создаёт самостоятельную запись. При откате вставки ключ остаётся свободен.

Ключ хранится в БД вместе с check-in, а на клиенте — пока открыт транскрипт.
Перезагрузка вкладки теряет локальный черновик. Явный reset удаляет check-in
вместе с его ключом.

## Конкурентные подтверждения

PostgreSQL сериализует подтверждение и PATCH текста по строке check-in.
Разные наборы для одной редакции текста получают последовательные ревизии
фактов. Каждый успешный POST возвращает снимок своего коммита. GET показывает
последнюю сохранённую версию и читает метаданные и факты одним SQL-запросом.
Идентичный набор, пока он текущий, возвращает ту же ревизию и safety-событие.
Если между двумя подтверждениями сохранён другой набор, новый запрос снова
считается явной заменой текущих фактов.

Факты, метаданные, safety snapshot и уведомления фиксируются одной SQL-
транзакцией. Ошибка записи уведомления откатывает всё подтверждение. Если
правка текста зафиксирована раньше, подтверждение старой редакции получает
409. Если подтверждение зафиксировано раньше, его ответ и историческое событие
сохраняют прежнюю редакцию, а GET после PATCH показывает новую редакцию без
текущих фактов. F7 закрыт по [повторной независимой приёмке](reviews/reacceptance-2026-11-11-mvp-6ffe7c5.md).

## Воспроизведение

Из корня проекта, с отдельной migrated `medsi_test_*` PostgreSQL-базой:

```bash
DATABASE_URL="$MEDSI_TEST_POSTGRES_URL" .venv/bin/alembic upgrade head
DATABASE_URL="$MEDSI_TEST_POSTGRES_URL" .venv/bin/alembic check
MEDSI_STORAGE=memory .venv/bin/pytest -q
npm --prefix frontend test
.venv/bin/python -m compileall -q backend experiments scripts
npm --prefix frontend run build
git diff --check
```

Без MEDSI_TEST_POSTGRES_URL PostgreSQL-кейсы явно skipped, а SQLite/memory
не называются PostgreSQL-проверкой. Два SQL-only кейса намеренно skipped только
для memory. В Node tests используются установленный TypeScript и node:test,
новых frontend-зависимостей нет. Они вызывают реальные обработчики App.tsx
с подменой только IO/state; браузерная проверка отдельно подтверждает связность UI.

Тесты: test_product_access_idempotency.py, test_event_identity_migration.py,
frontend/tests. Включены шесть одновременных анализов/подтверждений, шесть независимых
SQL repositories, принудительное нарушение unique-индекса и rollback notification.
Отчёт: `reviews/f4-f6-f7-f8-verification-2026-11-10.json`.
