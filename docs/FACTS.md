# Жизненный цикл подтверждённых фактов: facts-window-v1

Исправления F2/F3/F9 и текстового provenance, 10 ноября 2026 года.
Только синтетический прототип. Правила ниже — инженерный выбор для MVP,
а не клинически подтверждённые сроки актуальности жалоб.
Research-v2 использует собственный frozen протокол и не изменён.

## Актуальность обычных фактов (F2)

Для UTC-момента анализа T применимо включительное окно **[T − 24 часа, T]**.
Учитываются только факты подтверждённой текущей редакции check-in:

- `recorded_at` берётся из `check_ins.created_at`, а не из времени extraction;
- `confirmed_at` — серверное время сохранения подтверждения;
- требуется `T − 24h <= recorded_at <= confirmed_at <= T`;
- факт должен иметь ID, check-in ID и совпадающую текущую `text_revision`.

Позднее подтверждение старой записи не делает её новой. Будущая запись и
подтверждение после T не участвуют в историческом анализе. Окно — 24 UTC-часа,
а не календарный день профиля; timezone числового baseline остаётся прежним.
`temporal_context` сохраняется как подтверждённый текст, но не интерпретируется
как надёжная дата начала симптома: автоматического разбора относительных дат нет.

Отбор выполняется отдельно по category (strip + casefold; медицинские синонимы
не объединяются). Выбирается максимальная пара `(recorded_at, confirmed_at)`:
новая запись важнее старой, а повторное подтверждение разрешает равенство времени
записи. Отсутствие упоминания категории и проверенный пустой набор не отрицают её.

| Polarity последней записи | Влияние на обычный monitoring |
| --- | --- |
| present | Может дать attention при наличии хотя бы одной сравнимой числовой метрики |
| absent | Более раннее present этой категории не действует |
| uncertain | Более раннее present не действует; это не доказанное отрицание |

При точном равенстве обеих временных отметок и противоречащих polarity
автоматический положительный сигнал категории подавляется. Обе исходные
записи остаются в snapshot с `resolution=conflict`, без подмены их polarity.
Другие категории и числовые отклонения от этого не исчезают.

Отсутствие активного положительного факта не означает отсутствие симптомов.
При недостатке числовых данных обычные факты не отменяют `insufficient_data`.
Это сохранённая граница обычного MVP-monitoring; safety работает отдельно.

Исторический `as_of` ограничивает время доступных **текущих** фактов. Полная
реконструкция всех прошлых редакций/подтверждений не реализована: после правки
или повторного подтверждения новый исторический перерасчёт может отличаться.
Ранее сохранённое событие остаётся достоверным snapshot своего решения.

## Редакция текста и подтверждение (F3/F9)

У check-in есть `text_revision` (начиная с 1), `confirmed_revision` и
`confirmed_at`. `status=confirmed` означает совпадение текущей и подтверждённой
редакций, независимо от числа фактов. В том числе `facts: []` — проверенный
пустой результат, а не «все симптомы отсутствуют».

Минимальный контракт (`/api/v1/profiles/{id}/check-ins/{check_in_id}`):

1. GET возвращает текст, текущую редакцию, статус проверки и сохранённые факты.
   Те же поля присутствуют в POST создания, GET списка и caregiver summary.
2. PATCH: `{"text_revision":1,"corrected_text":"Слабости нет"}`. Если эффективный
   текст действительно изменён, revision увеличивается, прежние активные факты
   удаляются, состояние проверки сбрасывается. Сохранение того же текста не
   сбрасывает проверку. HTTP 409 означает устаревшую редакцию; нужно перечитать GET.
3. POST `/extract` возвращает `text_revision`, `awaiting_confirmation` и факты;
   не сохраняет их. Если текст изменён во время запроса провайдера, ответ — 409.
4. POST `/confirm`: `{"text_revision":2,"facts":[]}` либо список проверенных
   фактов. Evidence повторно валидируется относительно сохранённого текста.
   Необязательный legacy `corrected_text` допустим только равным этому тексту;
   менять текст следует отдельным PATCH. Устаревшая revision/другой текст — 409,
   пропущенная revision/невалидная цитата — 422. Ошибка не заменяет текущие факты.

SQL подтверждает/редактирует запись в транзакции с row lock и проверкой revision
в UPDATE. Факты подтверждения возвращаются из этой операции, без повторного
чтения потенциально уже заменённого набора. В памяти действует тот же контракт.

UI показывает серверный статус, позволяет удалить отдельный/последний факт,
подтвердить пустой набор и перечитать сохранённую запись. При несохранённом
изменении текста extraction/confirmation отключены; ответы старых UI-запросов
отбрасываются. После сохранения новой редакции требуется новая проверка.
Последний check-in ID локально запоминается для восстановления через GET после
перезагрузки страницы; сами факты и состояние проверки берутся с сервера.

## Неизменяемые доказательства события

Новые analysis/events содержат `text_provenance`: независимый JSON snapshot
выбранных актуальных фактов, включая отрицания, неопределённость и конфликты.
Это входы, рассмотренные при решении; при недостатке числовых данных они могут
не менять итоговый статус. Для каждого факта сохраняются:

```json
{
  "check_in_id": "checkin-synthetic-example",
  "fact_id": "fact-synthetic-example",
  "text_revision": 1,
  "category": "weakness",
  "polarity": "present",
  "evidence": "чувствую слабость",
  "temporal_context": "сегодня",
  "recorded_at": "2026-11-10T10:00:00Z",
  "confirmed_at": "2026-11-10T10:01:00Z",
  "rule_version": "daily-multimetric-v2+facts-window-v1",
  "resolution": "latest"
}
```

Числовые пороги не изменились; комбинированная версия нового обычного события —
`daily-multimetric-v2+facts-window-v1`. ID факта сохраняется как исторический
идентификатор, без FK из JSON на изменяемую таблицу. Цитата и редакция остаются
доступными после замены фактов, правки текста и перезапуска SQL repository.
Reset демонстрационного профиля по-прежнему намеренно очищает его события.

Safety при явном подтверждении использует только подходящие present-факты
`safety-v1`; их snapshot имеет `resolution=direct_confirmation`. Обычное окно
24h, более позднее отрицание и редактирование не отменяют существующее
safety-событие/notification. Повторные safety-подтверждения пока могут создавать
дубли: F7 открыт. Автоматического закрытия safety-событий нет.

## Миграция и совместимость

Перед запуском обновлённого backend применить `alembic upgrade head`:
`0006_fact_lifecycle` добавляет revision/review-поля и nullable JSON provenance.
Старые события читаются с `text_provenance=[]`; недостающие доказательства не
выдумываются, остальные поля остаются прежними. Старым check-in задаётся revision
1, но подтверждение не восстанавливается эвристикой по количеству фактов:
точная проверенная редакция/время неизвестны. Требуется явное новое подтверждение.
Legacy факты не уничтожаются миграцией, но не участвуют как актуально проверенные.
API-клиенты PATCH/confirm необходимо обновить для передачи `text_revision`.

## Воспроизведение проверок

```bash
.venv/bin/pytest -q backend/tests/test_fact_lifecycle.py backend/tests/test_fact_migration.py
.venv/bin/pytest -q
.venv/bin/python -m compileall -q backend experiments
npm --prefix frontend run build
git diff --check
```

`test_fact_lifecycle.py` выполняет одинаковые сценарии в памяти, SQLite и,
при `MEDSI_TEST_POSTGRES_URL`, в отдельной migrated базе `medsi_test_*`.
Без переменной PostgreSQL-кейсы явно skipped. Пример только для выделенной
тестовой базы (проверки очищают synthetic-профиль):

```bash
createdb -h 127.0.0.1 -U postgres -O medsi medsi_test_facts
export MEDSI_TEST_POSTGRES_URL='postgresql+psycopg://medsi:medsi@127.0.0.1:5432/medsi_test_facts'
DATABASE_URL="$MEDSI_TEST_POSTGRES_URL" .venv/bin/alembic upgrade head
MEDSI_STORAGE=memory .venv/bin/pytest -q
unset MEDSI_TEST_POSTGRES_URL
dropdb -h 127.0.0.1 -U postgres medsi_test_facts
```

Это публичные synthetic credentials из `.env.example`, не реальные секреты.
Для существующей собственной конфигурации использовать её локально.
Live-свидетельство: `reviews/f2-f3-f9-verification-2026-11-10.json`.
