# Продуктовый числовой monitoring: daily-multimetric-v2

Исправления независимого аудита F1/F5/F10, 10 ноября 2026 года. Это отдельный
продуктовый расчёт; frozen research-v2, его генератор и метрики не меняются.
Порог и агрегации — технические правила прототипа, не медицинские нормы.

## Момент, период и актуальность

`POST /api/v1/profiles/{id}/analysis` принимает необязательный query-параметр
`as_of` (ISO 8601). По умолчанию — текущее серверное время UTC. Время без offset
считается UTC, как в observation API. Будущий `as_of` отклоняется с HTTP 422.
Для повторяемого анализа старой истории требуется явный исторический `as_of`.

Часовой пояс берётся из `profiles.timezone` (IANA ZoneInfo). В синтетическом
профиле default — `Europe/Moscow`. UI/API изменения timezone в этом блоке не
добавлены. В БД даты по-прежнему хранятся UTC; snapshot сохраняет timezone.

Пусть D — календарная дата `as_of` в часовом поясе профиля. Период текущего
анализа: от местной полуночи D до `as_of` включительно. Используются только
измерения `measured_at <= as_of`, а не порядок поступления. Измерение прошлого
дня не выдаётся за актуальное измерение D. Будущие числа не участвуют даже при
наличии в старой/внешней БД. `period_start`/`period_end` в событии — этот текущий
период, а границы baseline отдельно записаны для каждой метрики.

Это выбранный для MVP однодневный срез из предложенных ТЗ последних 1–3 дней.
Сегодняшний день может быть неполным; последующий ввод может законно изменить
его агрегат. Об этом свидетельствуют cutoff, время и исходные IDs в snapshot.

## Отбор и дневные агрегации

Поддерживаются сон, активность, пульс, систолическое и диастолическое давление.
Проверяются технический диапазон, unit, source, quality и cutoff. Записи с
`quality=questionable` исключаются из числового расчёта. `good` и `unknown`
допускаются; unknown сохраняется в качестве результата и не означает
подтверждённую точность измерения. Неверные legacy-значения не участвуют.

| Метрика | Один агрегат на локальный день |
| --- | --- |
| Сон (`hours`) | Последнее валидное суточное значение по measured_at |
| Активность (`minutes`) | Последнее валидное суточное значение по measured_at |
| Пульс (`bpm`) | Медиана валидных измерений дня до cutoff |
| Давление (`mmHg`), каждая компонента | Медиана валидных измерений дня до cutoff |

Сон и активность уже являются суточными значениями. Повторный ввод их не
суммируется. При нескольких различных значениях с одинаковым максимальным
timestamp используется медиана этих значений, с сохранением всех их IDs.
Таким образом, порядок ввода и порядок SQL-выборки не меняют результат.
Для пульса/давления медиана выбрана как устойчивая дневная характеристика;
она не является детектором краткого экстренного числового пика.

`source_observation_ids` текущей метрики содержит только строки, участвовавшие
в её агрегате. У baseline свой список IDs. `excluded_observation_ids` показывает
невалидные/сомнительные строки в рассматриваемом окне; более ранние суточные
редакции сна/активности заменены последними и не объявляются невалидными.

## Исторический baseline

Общее ядро `aggregate_daily`/`calculate_baseline` используется анализом и trends.
Историческое окно — локальные даты **[D − 14 дней, D)**, то есть D−14 … D−1.
Минимум — 7 валидных **различных дней**, а не 7 строк. Сутки D исключены целиком,
даже если запись в них сделана раньше cutoff. Пропуски не заменяются нулями.
Границы строятся в timezone профиля, а не вычитанием фиксированных UTC-часов;
проверены Москва и часовой пояс с переходом DST — America/New_York.

Центр — медиана дневных агрегатов; масштаб — `1.4826 * MAD`. При практически
нулевом MAD используется прежний fallback `max(abs(center)*0.05, 0.1)`.
`sample_count` теперь обозначает число валидных исторических дней. При менее
7 дней center/MAD/scale равны null; даты и исходные IDs доступной истории
всё равно сохранены. `abs(z) >= 2.5` означает attention; порог не подстраивался.

## Все метрики и общий результат

На каждую поддерживаемую метрику возвращается отдельный результат:

- `missing_measurement`: нет валидного измерения в текущем локальном дне;
- `insufficient_data`: измерение есть, но нет готового baseline;
- `no_change`: измерение и baseline есть, числовое отклонение не обнаружено;
- `attention`: измерение отклонилось относительно дневного baseline.

Приоритет объединения: attention любой метрики → общий attention, независимо
от недостатка данных других; иначе недостаточный baseline хотя бы одной
измеренной метрики → insufficient_data; иначе при наличии сравнимых нормальных
метрик → no_change; если нет актуальных измерений → insufficient_data.

Отсутствующие метрики не объявляются нормальными. Они не скрывают результат
имеющихся, но дают `data_complete=false`. Нормальный результат при неполном
наборе относится только к доступным сравнимым метрикам, а не ко всему состоянию
человека. Например, давление не обязательно вводится ежедневно, но его
отсутствие остаётся явным в snapshot.

Обычные подтверждённые факты теперь отбираются по текущей редакции и явному
24-часовому UTC-окну. Последнее absent/uncertain подавляет более старое present
той же категории; пустое подтверждение не означает отрицание. Исторический
cutoff исключает подтверждения из будущего. Полные правила F2/F3/F9, API revision,
ограничения исторического перерасчёта и snapshot: [FACTS.md](FACTS.md).
Комбинированная версия событий: `daily-multimetric-v2+facts-window-v1`.

## Контракт и сохранение

К AnalysisResponse и MonitoringEventResponse добавлен `analysis_details`:

- `as_of`, `timezone`, `period_start`, `period_end`, `data_complete`;
- `metrics`: метрика, статус, дневное value/unit, measured_at, day, quality,
  z_score, baseline, текущие и исключённые observation IDs;
- baseline: center/MAD/scale, sample_count, window_start/window_end,
  список исторических дней и IDs, aggregation и quality.

У объединённого события прежние верхние `metric`/`z_score` равны null —
один показатель больше не представляет весь анализ. Значения по отдельным
метрикам находятся в `analysis_details.metrics`. Верхний source list —
объединение использованных текущих и baseline observation IDs.

Миграция `0005_daily_monitoring` добавляет `profiles.timezone` и nullable JSON
snapshot в `monitoring_events`. Старые события сохраняются, их snapshot null;
для них не выдумываются отсутствующие подробности. Перед запуском backend:

```bash
.venv/bin/alembic upgrade head
```

Snapshot новых числовых событий переживает перезапуск хранилища. Миграция
`0006_fact_lifecycle` дополнительно сохраняет независимый текстовый provenance.

## Trends

`GET /profiles/{id}/trends?metric=sleep_hours&days=7` отдаёт до одной точки
на локальный календарный день за последние 7 отображаемых дней. По умолчанию
viewport заканчивается последним доступным валидным днём метрики (не будущим).
При явном `as_of` — локальным днём этого cutoff.

Параметр days ограничивает только viewport. Baseline каждой точки вычисляется
из полной доступной истории её предыдущих 14 дней, общим продуктовым ядром.
Поэтому одна и та же точка имеет одинаковый baseline при days=1/7/28.
Дополнительно возвращаются day, quality, текущие IDs и baseline_details.
События связаны с текущими IDs соответствующей метрики, а не с последней
случайно выбранной строкой всего профиля. Legacy-события используют прежние IDs.
