# Демонстрация MEDSI Care

Проверка от 11 ноября 2026 года использует синтетический профиль
`profile-demo`, PostgreSQL 18.6 и локальный браузер.

| Участок | Результат |
| --- | --- |
| Дата demo и monitoring | UI загрузил 63 измерения и 21 check-in по 11.11.2026 в Europe/Moscow. Анализ использовал 14 предыдущих дней. |
| ASR на аудиофайле | Реальный faster-whisper 1.2.1, base, CPU int8. Обработан WAV длительностью 4,046 с с вымышленной жалобой, синтезированной для проверки. |
| Микрофон браузера | Пользователь произнёс вымышленную фразу через MediaRecorder и сохранил транскрипт. |
| Реальный GigaChat | GigaChat-2 вернул один неподтверждённый факт по исправленному тексту через UI. |
| Браузер и PostgreSQL после ASR | Транскрипт из файлового API перенесён в текстовую форму. Проверены исправление текста, extraction, правка цитаты, confirmation, событие с provenance и caregiver read. |
| Полный сквозной путь от микрофона | Пройден с участием пользователя на шаге записи. В UI проверены правка, GigaChat, подтверждение, анализ, уведомление и повтор. |

Файловый ASR вернул «Сегодня очист вюса бас. Сабас, а я в ясу таром.».
Первый запуск в процессе занял 2,312 с с загрузкой модели из кэша. Повтор
на той же модели занял 0,624 с. HTTP-запрос с WAV занял 1,633 с.
Для extraction текст вручную исправлен на «Сегодня я чувствую слабость.
Слабость появилась утром.». Эти времена и транскрипт относятся к одному файлу.

Микрофонный транскрипт «Сегодня чувствую слабость, слабость появилась утром.»
сверен с вымышленной фразой. Добавлено «я» и уточнена пунктуация.
По исправленному тексту GigaChat-2 вернул факт `weakness`. PostgreSQL сохранил
`attention` с цитатой «я чувствую слабость» и редакцией текста 2.
В caregiver UI уведомление прочитано, повтор анализа сохранил его `read_at`.
Отдельные замеры длительности и времени обработки микрофонного аудио
в этом прогоне не сняты.

## Подготовка окружения

Команды выполнять из корня репозитория. Нужны Python >=3.12, Node/npm,
PostgreSQL и браузер с поддержкой MediaRecorder. Только localhost или HTTPS
для микрофона. Сначала установить зависимости, если ещё не установлены:

```bash
python3 -m venv .venv
.venv/bin/pip install -e 'backend[dev]'
npm --prefix frontend ci
cp .env.example .env
```

Не перезаписывать уже настроенный `.env`: копирование нужно только при первом
запуске. Установить в нём `MEDSI_STORAGE=postgres`, `DATABASE_URL` своей
локальной синтетической базы, `MEDSI_DEMO_MODE=true`.

Для PostgreSQL через Compose:

```bash
docker compose up -d db
set -a
source .env
set +a
.venv/bin/alembic upgrade head
```

Если Docker socket недоступен, использовать существующий локальный PostgreSQL
с корректным `DATABASE_URL`; этот путь уже проверен P0.8. Не выдавать запуск
на SQLite/in-memory за проверку PostgreSQL. Основную базу не удалять.

### Локальные credentials GigaChat

Секреты вводятся только в локальный файл вне Git, например в уже используемый
`/home/linuxoid/Projects/secret.env`, или в игнорируемый `.env`. Не отправлять
их в чат. Не хранить во frontend и не включать в видеозапись терминала.

Переменные:

- `GIGACHAT_AUTH_KEY`: Authorization Key проекта;
- `GIGACHAT_MODEL`: идентификатор модели, доступной этому проекту;
- `GIGACHAT_SCOPE`: scope проекта;
- `GIGACHAT_TIMEOUT_SECONDS`: например, 30;
- `GIGACHAT_BASE_URL` и `GIGACHAT_OAUTH_URL`: адреса из `.env.example`.

В реальной проверке этого блока использовалась доступная аккаунту `GigaChat-2`.
Это не гарантия её доступности другому проекту и не заявление о бесплатной квоте.
TLS-проверку не отключать; использовать доверенный сертификат сервиса.

Проверка адаптера отдельно от UI (использует внешнюю сеть и квоту аккаунта):

```bash
PYTHONPATH=backend .venv/bin/python -m scripts.gigachat_smoke \
  --env-file /home/linuxoid/Projects/secret.env \
  --output /tmp/medsi-gigachat-check-new.json
```

Команда отправляет фиксированное синтетическое сообщение, проверяет схему,
дословный evidence, `confirmed=false`, ошибку несуществующей модели и сетевой
timeout с намеренно микроскопическим лимитом. Она не сохраняет факты в БД,
не печатает токены/ключи/ответы ошибок провайдера и не перезаписывает отчёт.
Число/формулировки фактов внешней модели могут меняться. Ошибочные JSON,
пустой/выдуманный evidence и OAuth/completion timeout отдельно проверяются
контролируемым транспортом в unit-тестах, а не выдаются за ответы живой модели.

Запуск backend в том же терминале после `source .env`:

```bash
PYTHONPATH=backend .venv/bin/uvicorn app.main:app --app-dir backend \
  --env-file /home/linuxoid/Projects/secret.env --host 127.0.0.1 --port 8000
```

Uvicorn не переопределяет уже экспортированные переменные из env-file. Если
ранее экспортированы пустые `GIGACHAT_AUTH_KEY`/`GIGACHAT_MODEL` из `.env.example`,
перед запуском выполнить `unset GIGACHAT_AUTH_KEY GIGACHAT_MODEL` или оставить
GigaChat-настройки только в одном локальном файле. Значения не выводить.
Для режима без GigaChat достаточно не передавать его env-file; при отсутствии
credentials extraction вернёт контролируемую 503.

В другом терминале:

```bash
npm --prefix frontend run dev -- --host 127.0.0.1 --port 5173
```

Открыть `http://127.0.0.1:5173`. Frontend перенаправляет `/api` в backend на
порту 8000.

## Загрузка синтетического профиля

Войти как `demo-user / demo-user` и нажать «Загрузить демоданные».
Последний день сценария определяется часовым поясом профиля. Измерения и
check-in каждого дня ставятся на локальную полночь и хранятся в UTC.
Ответ содержит `seed`, `anchor_date`, `timezone` и объём сценария.
При стандартных 21 дне это 63 измерения и 21 check-in. UI добавляет сценарий
с `reset=false`. При последовательном повторе на ту же дату уже загруженные
записи сохраняются, как и вручную введённые данные.

Для чистого повтора в отдельном синтетическом профиле передать `reset=true`.
Эта операция удаляет его measurements, check-ins, facts, events и notifications.
Явная опорная дата должна быть не позже текущего дня профиля. Сценарий
воспроизводится при одинаковых seed, anchor_date, days и timezone.

```bash
TOKEN=$(curl --fail-with-body -sS http://127.0.0.1:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"demo-user","password":"demo-user"}' | \
  .venv/bin/python -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
curl --fail-with-body -sS http://127.0.0.1:8000/api/v1/demo/load-scenario \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"seed":20261110,"anchor_date":"2026-11-11","days":21,"reset":true}'
unset TOKEN
```

После API reset обновить страницу. Для проверки исторического сценария указать
`as_of` внутри его последнего дня. Для текущего дня подходит кнопка анализа.
Паттерн числовых изменений начинается с индекса 14. Для показа используйте
стандартные 21 день с доступной предшествующей историей.

## Голосовой сценарий

1. Открыть [локальный MEDSI Care](http://127.0.0.1:5173/) в браузере на машине с
   микрофоном. Войти как `demo-user / demo-user` и загрузить демоданные.
2. Нажать «Записать голос», разрешить микрофон и произнести «Сегодня я чувствую
   слабость. Слабость появилась утром.». Нажать «Остановить запись».
3. Дождаться транскрипта и нажать «Сохранить транскрипт». Сверить текст с фразой.
   При необходимости исправить поле «Текст для проверки» и сохранить правку.
   После сохранения кнопка показывает «Транскрипт сохранён». Чтобы продолжить
   работу из другого сеанса, нажать «Открыть последнюю запись».
4. Нажать «Извлечь факты». Сверить категорию, polarity и точную цитату.
   При необходимости уточнить цитату и нажать «Подтвердить факты».
5. Нажать «Запустить анализ». Для стандартного demo ожидается событие
   `attention` и `symptom:weakness` при подтверждённой слабости.
   Проверить `text_provenance` через GET `/api/v1/profiles/profile-demo/events`.
6. Войти как `demo-caregiver / demo-caregiver` и нажать «Прочитать» у уведомления.
7. Вернуться к владельцу, повторить анализ и проверить прежние event ID,
   количество уведомлений и `read_at`.

Для отдельной файловой проверки ASR можно отправить синтетический WAV через
multipart-поле `audio` на `POST /api/v1/profiles/profile-demo/audio/transcriptions`
с bearer-токеном владельца. Для стенда использованы `FASTER_WHISPER_MODEL=base`,
`FASTER_WHISPER_DEVICE=cpu`, `FASTER_WHISPER_COMPUTE_TYPE=int8` и язык `ru`.
Замер первого запуска включает загрузку из локального кэша, повторный замер
переиспользует экземпляр transcriber. HTTP-обработчик создаёт экземпляр для
каждого запроса. Сценарий с WAV и сценарий с микрофоном фиксируются отдельно.

## Сеть, резервный режим и восстановление

- GigaChat требует сети, credentials и доступной квоты. OAuth, модель, TLS,
  rate limit и timeout могут прервать extraction. Автоматического локального
  LLM-подменщика нет.
- При 502/503 UI явно показывает «Резервный режим». Новые факты не сохраняются;
  ручной дневник, история и числовой monitoring продолжают работать при
  доступном backend. После восстановления сети повторить extraction вручную.
  Уже подтверждённые факты не удаляются при отказе новой попытки.
- Потеря связи с backend — отдельный отказ: запись в БД не гарантируется,
  интерфейс сообщает об отсутствии связи. Это не офлайн-приложение.
- faster-whisper работает локально после установки/кэширования модели.
  Нет микрофона/ошибка ASR — явно перейти к ручному тексту; это резервный путь,
  не доказательство распознавания речи. Аудио не сохраняется в Git.
- При 422 исправить единицы/значение/дату или evidence, а не ослаблять проверку.
- При 403 использовать правильную роль. При просроченном токене войти снова.
- После перезапуска in-memory теряет данные; для основной демонстрации
  использовать PostgreSQL и миграции. При необходимости повторить loader/reset.
